1. Introduction

1.1 What Plan Console is

Plan Console is a small desktop application (one Python file, no installer, no pip dependencies) that turns rough text — a plan, a brainstorm, or an audit report — into a disciplined, gated software project that a coding agent executes for you, session by session, under your control.

It is a Tkinter app: double-click it and a window opens. It runs fully offline except for one optional feature (fetching the OpenRouter model list and, if you opt in, one model call during intake).

1.2 The problem it solves

Handing a task to a coding agent is easy. Keeping it on track is not. Agents drift, skip steps, invent facts, declare victory early, and leave no trace of what was decided or why. Plans die from skipped steps and unanswered questions.

Plan Console fixes this with structure instead of supervision:

  • Every plan starts from a saved source document (SOURCE.md).
  • Facts are verified before work begins (a recon checklist).
  • Decisions only you can make are parked as open questions and must be answered before anything is locked.
  • The plan is "frozen" only after every gate passes — then it is the single source of truth.
  • Work happens in numbered sessions with a strict order, a completion record per session, and a verdict you check after each one.
  • Nothing jumps ahead: session 3 will not run before sessions 1 and 2 have OK records.

1.3 Who it's for

  • Owners of any coding agent (command-line agents, IDE agents, or standalone tools) who want repeatable, auditable results instead of chat roulette.
  • Novices: the console tells you exactly what to paste, when, and what to check. The bundled sample project shows every artifact in its finished state before you run anything live.
  • Experienced users: the gates, verdicts, standing orders and file conventions are plain text in your repo — inspectable, editable, and scriptable.

1.4 How it works at a high level

You are the owner. The console is the paperwork machine. The agent is the workforce.

  • YOU plan: paste text into the Intake tab, answer the questions only you can answer (the "owner pass"), and freeze the plan.
  • THE CONSOLE manages files: it scaffolds plans/<slug>/ in your repo, generates ready-made instructions for the agent, checks the agent's work, and enforces the gates.
  • THE AGENT executes: you paste the console's instruction into your coding agent with your repo open as the workspace; the agent reads the rulebook (PART-00.md), does the scoped work, and writes its completion record back into the plan folder.

The console and the agent never talk to each other directly. All communication goes through your clipboard and through files in your own repository — which is why Plan Console works with any capable agent and why, without an API key, nothing ever leaves your machine.

2. Installation

2.1 Requirements

  • Python 3.9 or newer, with Tkinter (Tkinter is included in the standard installers from python.org; on some Linux distributions it is a separate package, see 2.4).
  • Zero pip dependencies. Plan Console uses only the Python standard library.
  • An operating system with a desktop (Windows, macOS, Linux).
  • Optional: pytest, only if you want to run the project's own test suite.
  • Network access is needed ONLY for the optional OpenRouter model list and the optional intake model call. Everything else is offline.

2.2 Windows

  1. Install Python from python.org/downloads — tick "Add python.exe to PATH" during setup.
  2. Put plan-console.py and plan.bat in any folder (for example C:\Tools\PlanConsole).
  3. Double-click plan.bat. It finds a usable Python even when the Microsoft Store "python stub" is installed (the stub that opens the Store instead of running Python).

2.3 macOS

  1. Install Python 3 from python.org (the installer includes Tkinter; the macOS system Python may not).
  2. Put plan-console.py in any folder.
  3. In Terminal: python3 plan-console.py

2.4 Linux

  1. Install Python 3 and Tkinter. Examples:
    • Debian/Ubuntu: sudo apt install python3 python3-tk
    • Fedora: sudo dnf install python3-tkinter
    • Arch: sudo pacman -S tk
  2. Put plan-console.py in any folder.
  3. Run: python3 plan-console.py

2.5 Checking Python and Tkinter

In a terminal:

python --version        (Windows)   or   python3 --version
python -c "import tkinter"          (should print nothing = OK)

If the version is below 3.9, or the import fails, install a current Python from python.org (Windows/macOS) or your package manager (Linux, with the tk package).

2.6 Troubleshooting installation

  • "python is not recognized" — Python is not on PATH. Re-run the installer and tick "Add python.exe to PATH", or use plan.bat.
  • The Microsoft Store opens when you type python — that is the Store stub. plan.bat handles it; otherwise disable the stub in Settings > Apps > App execution aliases.
  • "No module named tkinter" — install the Tk package for your distribution (see 2.4) or reinstall Python from python.org with tcl/tk enabled.
  • Headless server / no display — Tkinter needs a desktop; run the app on a machine with a GUI.

3. First launch

3.1 The splash screen

At launch a small borderless splash window appears for a moment, showing the app name (Plan Console), the version (1.1.0), the tagline ("Paste-to-plan intake + session lifecycle manager"), the copyright line, and the Apache 2.0 licensing note. It disappears by itself when the main window is ready. If anything goes wrong with the splash, the app still starts normally.

3.2 First-run license and disclaimer acceptance

The first time Plan Console starts, an acceptance window opens showing the full Apache License 2.0 text and the legal disclaimer, each with its own "I agree" checkbox. The I Agree button stays disabled until both checkboxes are ticked — one accepting the Apache License 2.0 terms, one accepting the legal disclaimer (the app is provided "as is", with no warranties and no liability — full text in section 13). If you do not agree with one or both, close the window or decline: the application exits.

What is stored, and where: your acceptance is written to plan-console.json, in the same folder as plan-console.py, as:

"license_accepted":         true
"license_accepted_version": "Apache-2.0"
"license_accepted_date":    <ISO date, e.g. 2026-09-05>

On every later launch a truthy license_accepted skips the dialog.

To see the license again at any time, click the About button in the top bar and then View License. The About box also shows a clickable link to apache.org/licenses/LICENSE-2.0.

To reset acceptance (for example to review the license again), open plan-console.json in a text editor and delete the "license_accepted" key (or the whole file — see section 9 for what else that resets), then start the app.

If plan-console.json is corrupted (undecodable), the app backs it up as plan-console.json.corrupt, starts with empty settings, and asks for acceptance again. Your plans in the repo are never touched by this.

4. Core concepts

Repo folder — the project folder your agent works on. The console writes its paperwork there (PART-00.md, templates/, commands/, plans/). You point the app at it with Browse… and initialize it with Init starter repo.

Plan — one unit of work, living in plans/<slug>/ inside the repo. A plan goes: source text → draft → owner pass → validation → frozen plan → sessions → PLAN COMPLETE.

Slug — the plan's short name, lowercase-with-dashes (kebab-case), e.g. payments-v2. It becomes the folder name under plans/. The console remembers your last slug and a dropdown of recent slugs (per repo) on all three tabs.

SOURCE.md — the permanent record of the text you pasted at intake. Frozen at creation; the plan is always traceable back to what you started from.

Draft (PART-01.draft.md) — the editable plan in the standard form, produced from your source text. You and the agent refine it here until the gates pass.

Freeze — the act of locking the draft into the official plan, PART-01 v1.0.md (the version lives in the filename). Freeze is gated: it refuses while anything is open. Frozen means locked.

Gates — the four conditions Freeze checks: 0 open questions, 0 unchecked recon items, 0 unchecked owner actions, and VALIDATION.md reading exactly PART-01 READY.

Session — one scoped unit of agent work from the frozen plan's session list. You copy a session instruction, paste it into your agent, and afterwards record a verdict. The last session is the deploy session, marked [DEPLOY] in the plan.

Owner pass — the only manual thinking step: answering the questions the agent parked for you (OPEN-QUESTIONS.md), ticking the recon checklist, and handling owner actions (commands the agent must never run).

Standing orders (AGENT-ORDERS.md) — your persistent rules for the agent ("always write tests", "never push to main"), embedded in every session instruction. Edit them via the Agent orders… button.

Verdicts — after each session, Session report returns one of: OK (complete; the number auto-advances), ⚠ CHECK (something is off, usually a completion line not in the exact required format; a "fix:" hint is copied to your clipboard), ✖ BLOCKED (the agent wrote BLOCKED.md explaining what stopped it), or ✖ INCOMPLETE (no completion record at all).

5. Step-by-step walkthrough

A full worked example, end to end. At every step, the bundled sample project shows the exact artifact this step produces — open it via Open sample project… (see 3.4). The scenario: a small offline CLI ("rc") that manages a personal recipe collection.

Step 1 — Point the console at a repo

Click Browse… and choose your project folder (first time? create an empty test folder, or use the sample). Click Init starter repo. This writes PART-00.md (the rulebook), templates/PART-01.md (the blank plan form) and commands/ (7 instruction files) into the repo. Existing files are never overwritten.

Reference: the sample repo already has these — see samples/demo-project/.

Step 2 — Intake

Open the Intake tab. Paste your text (for the demo: a short brief describing the "rc" recipe CLI). Pick the Type: plan for a finished plan, brainstorm for rough ideas, audit for an audit report. Type a slug, e.g. recipe-cli. Click Proceed.

The console saves your text as plans/recipe-cli/SOURCE.md and produces the plan files (see step 3). With a key it can call the model itself; without one it hands you a ready-made instruction to paste into your agent.

Reference: samples/demo-project/plans/demo-recipe-cli/SOURCE.md shows exactly what this step stores.

Step 3 — The plan files appear

In plans/<slug>/ you now have PART-01.draft.md (the draft plan), RECON-CHECKLIST.md (facts to verify) and OPEN-QUESTIONS.md (decisions only you can make). For an audit intake, also TRIAGE.md sorting findings into fix-now / later / accept.

Reference: the same three files (plus the finished versions of each) in samples/demo-project/plans/demo-recipe-cli/.

Step 4 — The owner pass

Open the Owner pass tab, type the slug, click Refresh.

  • Questions: for each open question, either click Accept recommendation (when the block carries a RECOMMEND: line you agree with) or type your answer and click Save answer → draft + remove. Answers land in the draft under ## OWNER ANSWERS; the question is removed from OPEN-QUESTIONS.md.
  • Recon checklist: items the agent could verify are already ticked [x]. Run the remaining checks yourself and change [ ] to [x] (or delete lines you decide to skip; an item you consciously postpone is marked DEFERRED with a reason).
  • Owner actions (right panel): commands needing your passwords or dashboards. Whitelisted read-only ones get a Run (read-only) button; anything else, Copy command, run it yourself, then Mark done.

Reference: samples/demo-project/plans/demo-journal-wip/ is frozen mid-owner-pass — exactly what this step looks like before it is done; demo-recipe-cli/OPEN-QUESTIONS.md shows the finished state (0 open questions, owner actions done).

Step 5 — Validate, then freeze

Click Validate draft for a gap-report (written to VALIDATION.md and shown in the log). If findings remain, click Auto-resolve findings to chain the fixes and a re-validation. When VALIDATION.md reads exactly PART-01 READY and nothing is open, click Freeze. PART-01 v1.0.md is created — the locked official plan with its session list.

Reference: samples/demo-project/plans/demo-recipe-cli/VALIDATION.md (says PART-01 READY) and PART-01 v1.0.md (the frozen plan).

Step 6 — Run sessions

Open the Sessions tab, type the slug, set the session number (start with 1), click Copy session instruction, and paste it into your coding agent with the repo open as the workspace. When the agent finishes, click Session report and act on the verdict (OK / ⚠ CHECK / ✖ BLOCKED / ✖ INCOMPLETE — see 6.9). Repeat for each session. The last session is the deploy session — stay and watch it.

Reference: samples/demo-project/plans/demo-recipe-cli/PROGRESS.md shows a full session history, including a BLOCKED session that was fixed and re-run to PASS.

Step 7 — Close out

Click Plan health before the deploy session (the "pre-deploy sweep") and whenever you return to a plan after a break. When all sessions pass, health tells you to append "PLAN COMPLETE <date>" to PROGRESS.md. The plan is done.

Reference: samples/demo-project/plans/demo-recipe-cli/HEALTH.md and the closing lines of its PROGRESS.md.

The whole loop on one page (cheat sheet)

  1. Paste brainstorm/audit/plan → type + slug → Proceed
  2. Answer OPEN-QUESTIONS (Accept recommendation or type + save)
  3. Run owner-only checks → tick [x] in RECON-CHECKLIST
  4. Validate draft → Auto-resolve findings → repeat until READY
  5. Freeze
  6. Sessions tab: slug + 1 → Copy session instruction
  7. Paste into your agent (repo open as workspace)
  8. Watch it work
  9. Session report → verdict
  10. verdict OK → next session number → back to 6
  11. verdict ⚠ CHECK → fix hint is on your clipboard → paste → Session report again
  12. verdict ✖ BLOCKED → fix cause → rename BLOCKED.md to BLOCKED-resolved.md → re-run
  13. Last session = deploy, supervised → Plan health → PLAN COMPLETE

6. Every major feature in depth

6.1 Repo folder and Init starter repo

The Repo folder field (top bar) is where all paperwork lives. Click Browse… to choose it; the choice is remembered. Init starter repo writes, without ever overwriting existing files:

  • PART-00.md — the rulebook every agent session must follow
  • templates/PART-01.md — the blank plan form
  • commands/ — 7 instruction files (new-plan, recon, owner-resolve, validate-plan, freeze-plan, session, plan-status)

"Not a plan repo" means these are missing — click Init starter repo.

6.2 Update command files (and the auto-update check)

The console ships with built-in command protocols. Update command files refreshes your repo's commands/ with the current built-in versions — but never overwrites a file you have customized (it compares content and only touches stale or missing ones).

About 400 ms after start, the console runs the same check silently. If newer built-in protocols exist, a dialog tells you exactly what changed (one-line note) and offers to update. Declining changes nothing.

6.3 Intake: types, slug, Proceed

Paste your text into the big box, pick the Type, type the slug, and click Proceed:

  • plan — a finished plan/task description.
  • brainstorm — rough ideas; the agent distills them into a coherent draft and lists what needs your decision.
  • audit — an audit report; the agent also writes TRIAGE.md sorting every finding into fix-now / fix-later / accept.

Your text is saved as plans/<slug>/SOURCE.md (permanent record). The draft scaffolding then runs: with a key, the console calls the model itself; without one, a popup gives you a ready-made instruction to paste into your agent (a backup of every instruction is kept in plans/<slug>/instructions/). Everything the console did appears in the log at the bottom.

6.4 Open sample project…

Copies the bundled samples/demo-project/ into a folder you choose and points the Repo folder there. If the chosen folder is not empty, the console warns you before copying files with clashing names. Use it to explore a finished plan (demo-recipe-cli) and a mid-workflow plan (demo-journal-wip) before running anything live.

6.5 The Owner pass

Open the Owner pass tab, type the slug, click Refresh. The tab loads three things:

Open questions (left panel) — questions from OPEN-QUESTIONS.md, shown as three-line PROBLEM / QUESTION / RECOMMEND blocks. Blocks with a RECOMMEND: line are marked with a "has rec" suffix.

  • Agree with the recommendation? Select the question and click Accept recommendation. It shows you the recommendation, asks for confirmation, then saves it as your answer (stamped [recommendation accepted <date>]) and removes the question. Questions without a RECOMMEND line get a clear error — type those in the answer box instead.
  • Know the answer yourself? Type it in the answer box and click Save answer → draft + remove. The answer lands in PART-01.draft.md under ## OWNER ANSWERS and the question is removed from OPEN-QUESTIONS.md (a .bak snapshot is kept first, and the exchange is archived to owner-pass.log).
  • Changed your mind about a question entirely? Archive question (keep log) removes it without answering; the whole block is kept in owner-pass.log.

Owner actions (right panel) — commands the agent may never run: anything needing your passwords, dashboards or owner-only files, listed from ## Owner actions in OPEN-QUESTIONS.md.

  • Whitelisted read-only commands (Select-String, Test-Path, Get-Content, git status/diff/log) get a Run (read-only) button: the console runs the command in your repo, shows the output in the log, and — after you confirm — marks the linked §B line VERIFIED <today> in the draft and ticks the action done.
  • Anything else: Copy command, run it in your own terminal, then Mark done.
  • Nothing runs or is written without your confirmation; every event is archived to owner-pass.log.

Recon checklist — shown with the questions. Items the agent could already check are ticked [x] for you. Items left for you: run the check, then change [ ] to [x] in RECON-CHECKLIST.md (or delete lines you decide to skip). A line marked DEFERRED means a deliberate, documented decision to skip that item — it counts as settled and does not block Freeze, but the reason stays on the record.

What's blocking Freeze? (top of the tab) — a read-only dry-run that lists exactly what would block Freeze right now — open questions, unchecked owner actions, unchecked recon items, a missing or not-ready validation report — without changing anything. Use it any time you want to know why Freeze is refusing.

6.6 Validate draft and the validation gap report

Click Validate draft. With a key the console asks the model to write a gap-report on the current draft; without one it gives you a ready-made instruction for your agent. Either way the report lands in plans/<slug>/VALIDATION.md and is shown in the log. It lists every gap between the draft and a freeze-ready plan, each with a remediation line (in "→ run owner-resolve <slug>" style) that Auto-resolve findings can act on. A report whose entire content is exactly PART-01 READY means zero gaps: Freeze is unblocked. Click Show validation report to re-read the latest report at any time.

6.7 Auto-resolve findings

Auto-resolve findings parses VALIDATION.md and chains the remediation for you:

  • With a key: the console dispatches the owner-resolve step (answers questions, applies the draft fixes the findings call for) and then re-validation, back to back, and tells you when VALIDATION.md says PART-01 READY.
  • Without a key: it copies one ready-made instruction that makes your agent do both steps back to back. Paste it, let the agent finish, and the fresh report supersedes the old one.

When the "auto-resolve findings" checkbox (Intake tab) is ticked, this chain also runs automatically after Validate draft. If VALIDATION.md already says PART-01 READY, the button tells you there is nothing to resolve.

6.8 Freeze and the freeze gates

Freeze locks the draft into the official plan. It refuses — with a message naming the offender — unless all four gates pass:

  1. 0 open questions in OPEN-QUESTIONS.md
  2. 0 unchecked recon items ([ ]) in RECON-CHECKLIST.md
  3. 0 unchecked owner actions
  4. VALIDATION.md reads exactly PART-01 READY

On success the frozen plan is written as PART-01 v1.0.md (the version lives in the filename) together with its session list. Frozen means locked. If you must change it later, edit it and add " | v1.1 frozen <date>" to its first line, and note why in PROGRESS.md.

6.9 Sessions: the daily loop

  1. Open the Sessions tab. Type the slug, set the session number (start with 1).
  2. Click Copy session instruction. The instruction embeds your standing orders from AGENT-ORDERS.md plus the exact scope of this session: which rules file to load, what to do, what to record.
  3. Paste it into your agent (repo open as the workspace) and let it work. The agent records its completion when done.
  4. Back in the console, click Session report. You get a verdict:
    • OK — session complete. The session number advances by 1 automatically (never past the deploy session).
    • ⚠ CHECK — something's off (usually the agent did not write its completion line in the exact required format). The report shows a "fix:" hint and it is copied to your clipboard automatically — paste it into your agent and click Session report again.
    • ✖ BLOCKED — the agent hit a wall and wrote BLOCKED.md explaining what stopped it and what it tried. Fix the cause (often you must run a command or provide access), rename BLOCKED.md to BLOCKED-resolved.md, and re-run the session.
    • ✖ INCOMPLETE — no completion record at all; the session never really finished.
  5. On OK the number is already advanced; otherwise increase it by 1 and repeat.

You cannot jump ahead: session 3 will not run before sessions 1 and 2 have OK records. That is deliberate — plans die from skipped steps.

The last session is the deploy session (marked [DEPLOY] in the plan). Run it the same way but stay and watch: the instruction makes the agent run its checks before AND after deploying, and stop immediately if a post-deploy check fails.

Split-deploy sessions (v3.6, optional): a plan's §A may mark a deploy session with split, pre+post, pre-post, or pre/post in the deploy? cell. This splits the session into two legs — Na (pre-deploy) and Nb (post-deploy) — each with its own canonical PROGRESS line (SESSION 6a / SESSION 6b). Plan health renders two rows ([DEPLOY-PRE] / [DEPLOY-POST]) and shows a DEPLOY WINDOW verdict when leg a is done but leg b awaits the owner's deploy: the owner runs the deploy (e.g. Coolify) and the agent has nothing to run until the deploy completes. The Copy-session-instruction leg selector (full / a / b) produces per-leg instruction files. Unmarked plans are byte-for-byte unchanged — no marker means no legs, no selector, no new behavior.

6.10 Plan health and Status

Plan health — click it any time for one line per session: what's done, what's broken, what's next. Always click it before the deploy session (the "pre-deploy sweep") and when returning to a plan after a break. Every health run is appended to plans/<slug>/HEALTH.md, so each plan keeps its own history of checks. Status is the quicker one-line "where am I". When all sessions pass, health tells you to append "PLAN COMPLETE <date>" to PROGRESS.md — paste that hint into your agent or add the line yourself. The plan is done.

For split-deploy sessions, Plan health shows a DEPLOY WINDOW verdict when leg a is done and leg b has not run: the owner runs the deploy now, then copies the leg b (post-deploy) instruction. The agent has nothing to run during the deploy window.

6.11 Agent orders (standing orders)

Agent orders… (top bar) opens AGENT-ORDERS.md from the repo root — the standing orders attached to every session instruction. Typical entries: "always write tests", "never push to main", "match the existing code style". Edit freely; the next Copy session instruction picks up your changes. The file is only created if missing — your customized text is never overwritten by the app.

6.12 API key and model selection

The OpenRouter key is optional. Paste it in the top bar and tick "Use API key" (or set the OPENROUTER_API_KEY environment variable — the field stays empty and the env value is used instead; it is never persisted). Click Reload models to fetch the live model list — free models end in :free — and pick a favorite; your picks are remembered at the top of the list. The model is used only by the console for the intake and auto-resolve steps; sessions always run in your agent, with whatever model you chose there. The key is kept in memory for the current session only and is never written to disk.

6.13 Themes and window size

Theme (top bar): Light, Dark, or Follow OS. Follow OS matches your system personalization and switches automatically. On Windows high-contrast mode the app steps aside entirely and lets the OS colors rule. Your choice is saved in plan-console.json. The window starts maximized (full screen) and is freely resizable (smallest 820 × 600); the size you close it with is remembered for the next start.

7. Working without an API key

The OpenRouter key is entirely optional. Plan Console is built agent-agnostic: it hands ready-made instructions to your coding agent (Zoo Code, Claude Code, Cursor, Codex, or any other), which does the actual work inside your repository. Without a key the app is not a "demo mode" — it is the full product.

The key only changes who scaffolds the first draft: the console's model call, or your own agent via a pasted instruction. Everything else — owner pass, validation, auto-resolve, freeze gates, sessions, plan health, themes, the sample project — is identical with or without a key. Without a key the console makes no network calls at all.

The companion guide no-api-key-guide.html (top-bar link "How to use without a key (guide) »") covers this workflow in depth, step by step.

Writes are atomic (a temp file is replaced into place), so a crash mid-write cannot corrupt the file. If the file is ever undecodable, it is backed up as plan-console.json.corrupt and settings restart empty — nothing crashes.

Privacy and security

  • The API key is never written to disk. It lives in memory for the current session only, or comes from the OPENROUTER_API_KEY environment variable. Legacy keys found in old config files are removed on load.
  • Network is used ONLY for the optional OpenRouter model list and the optional intake/auto-resolve model calls. Without a key the console makes no network calls at all. Everything else — plans, files, guides, themes — is fully offline.
  • What leaves your machine is only what you choose to send: the model calls (if you use a key) and whatever you paste into your coding agent.
  • Owner actions run only after your explicit confirmation, and only whitelisted read-only commands (Select-String, Test-Path, Get-Content, git status/diff/log) can be run from inside the app. Every owner-pass event is archived to owner-pass.log.
  • To reset acceptance or all settings, delete the corresponding keys (or the whole file) in plan-console.json — see sections 3.2 and 12.

11. FAQ

Do I need an API key?

No. See section 7 — the copy-paste workflow is the full product.

Which coding agents can I use?

Any capable one: Zoo Code, Claude Code, Cursor, Codex and others. The instructions are plain text with explicit file paths and formats, so nothing is tied to one product.

Is my API key safe?

Yes — it is never written to disk, only kept in memory for the current session (or read from the OPENROUTER_API_KEY environment variable). Legacy stored keys are removed on load.

Where do my plans live?

In your repo, under plans/<slug>/. The app folder holds only settings (plan-console.json) and the guides. Deleting the app never touches your plans.

What happens if I close the app mid-step?

Nothing is corrupted. Files are only written when a step completes, config writes are atomic, and plans live in your repo.

Can I run several plans at once?

Yes — each plan is its own plans/<slug>/ folder. The console works on the slug you type; switch by typing another slug.

Can I use one console for several repos?

Yes. Switch the Repo folder; the dropdown history adapts (recent slugs are filtered to the plans that exist in the current repo).

Why can't I jump ahead to session 3?

Deliberate design — plans die from skipped steps. Sessions must pass in order; the console enforces it.

How do I change a frozen plan?

Edit PART-01 v1.0.md and add " | v1.1 frozen <date>" to its first line, then note why in PROGRESS.md. Nothing stops you, but the version trail keeps the change honest.

What does DEFERRED mean on the recon checklist?

A documented decision to skip that item. It counts as settled and does not block Freeze; the reason stays on the record.

Does the console send my code anywhere?

No. Only the optional OpenRouter calls leave the machine (the text you pasted plus short prompts), and only if you use a key. Without a key there are no network calls at all.

Do free OpenRouter models work?

Yes — models ending in :free cost nothing. If a free model is rate-limited (HTTP 429), wait or switch models.

How do I reset the license acceptance or all settings?

Delete the license_accepted key (acceptance only) or the whole plan-console.json (everything) while the app is closed.

12. Advanced usage

Customizing AGENT-ORDERS.md

Agent orders… opens the repo's standing orders. They are embedded verbatim into every session instruction, so house rules (test policy, branch policy, style rules) are enforced without you repeating them. Keep lines short and imperative. The file is yours — the app never overwrites it.

Editing command files safely

The 7 files in commands/ are plain Markdown instructions. You can edit them, but the auto-update check (about 400 ms after start, and Update command files) compares content: customized files are never overwritten, stale or missing ones are refreshed. If you edit one, expect the updater to leave it alone. To adopt a newer built-in version, diff your changes back in by hand.

Using different agents

The console only produces text and reads files. Any agent that can read a workspace, follow written instructions, and write files works. Point it at the repo, paste the instruction, done. Mixing agents across sessions of one plan also works — PROGRESS.md keeps the thread.

Multi-repo habits

plan-console.json is shared by every repo the console points at. recent_slugs is filtered against the current repo's plans/, so the dropdown only offers slugs that exist where you are. Favorites and theme are global. If you share one config across very different repos, expect the slug history to be a merged view.

Running the tests

The project ships a pytest suite (test/). Install pytest once (pip install pytest) and run py -m pytest test/ -q (Windows) or python3 -m pytest test/ -q from the app folder. Tests are optional for using the app.

Config surgery

plan-console.json is plain JSON. With the app closed you can edit any key: point repo at another checkout, prune favorites, clear recent_slugs, or flip theme. A broken file is not fatal — the app moves it to plan-console.json.corrupt and starts fresh. Deleting keys restores their defaults on the next save.
